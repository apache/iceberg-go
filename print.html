Iceberg Golang

Iceberg Go

Apache Iceberg Go is a Go-native implementation of Apache Iceberg, the open table format for analytic datasets. Read and write Iceberg tables from Go services and tooling without a JVM.

Where to start

  • Install - get the library and CLI on your machine.
  • CLI - inspect tables, run maintenance, manage refs.
  • API - construct catalogs, scan tables, write Arrow data, evolve schemas.
  • Configuration - YAML config file, catalog options, FileIO and credentials, table properties.

What works today

A capability matrix - filesystem, metadata operations, catalog support, and write operations - lives on the dedicated Feature Status page.

Beyond Go

Apache Iceberg is multi-language. PyIceberg, iceberg-rust, iceberg-cpp, and the Java reference implementation all target the same spec - see Other Iceberg implementations for cross-links.

Getting Started

Create an Iceberg table in a local SQLite catalog, append three rows with Arrow, and read the rows back. The program uses a fresh temporary catalog and warehouse on each run and removes them when it exits.

Install

This walkthrough uses Iceberg Go v0.7.0 and requires Go 1.25.9 or later. Create a new directory and run:

go mod init iceberg-go-tutorial
go get github.com/apache/iceberg-go@v0.7.0 \
  github.com/apache/arrow-go/v18@v18.8.0 \
  github.com/uptrace/bun/driver/sqliteshim@v1.2.18

Create, write, and read a table

Save the following as main.go. The SQL catalog stores table registrations in SQLite. The Iceberg metadata and Parquet data files go in the local warehouse.

package main

import (
	"context"
	"fmt"
	"io"
	"log"
	"os"
	"path/filepath"

	"github.com/apache/arrow-go/v18/arrow"
	"github.com/apache/arrow-go/v18/arrow/array"
	"github.com/apache/arrow-go/v18/arrow/memory"
	"github.com/apache/iceberg-go"
	"github.com/apache/iceberg-go/catalog"
	_ "github.com/apache/iceberg-go/catalog/sql"
	"github.com/uptrace/bun/driver/sqliteshim"
)

func run(ctx context.Context) error {
	dir, err := os.MkdirTemp("", "iceberg-tutorial-")
	if err != nil {
		return err
	}
	defer os.RemoveAll(dir)

	cat, err := catalog.Load(ctx, "tutorial", iceberg.Properties{
		"type":        "sql",
		"uri":         "file:" + filepath.Join(dir, "catalog.db"),
		"sql.driver":  sqliteshim.ShimName,
		"sql.dialect": "sqlite",
		"warehouse":   "file://" + filepath.Join(dir, "warehouse"),
	})
	if err != nil {
		return err
	}
	if closer, ok := cat.(io.Closer); ok {
		defer closer.Close()
	}

	if err := cat.CreateNamespace(ctx, catalog.ToIdentifier("taxi"), nil); err != nil {
		return err
	}
	trips := catalog.ToIdentifier("taxi", "trips")
	schema := iceberg.NewSchema(0, iceberg.NestedField{ID: 1, Name: "trip_id", Type: iceberg.PrimitiveTypes.Int64, Required: true})
	tbl, err := cat.CreateTable(ctx, trips, schema)
	if err != nil {
		return err
	}

	arrowSchema := arrow.NewSchema([]arrow.Field{{Name: "trip_id", Type: arrow.PrimitiveTypes.Int64}}, nil)
	records := array.NewRecordBuilder(memory.DefaultAllocator, arrowSchema)
	defer records.Release()
	records.Field(0).(*array.Int64Builder).AppendValues([]int64{1, 2, 3}, nil)
	batch := records.NewRecord()
	defer batch.Release()
	input := array.NewTableFromRecords(arrowSchema, []arrow.Record{batch})
	defer input.Release()
	tbl, err = tbl.AppendTable(ctx, input, 1024, nil)
	if err != nil {
		return err
	}

	output, err := tbl.Scan().ToArrowTable(ctx)
	if err != nil {
		return err
	}
	defer output.Release()
	if tbl.CurrentSnapshot() == nil || output.NumRows() != 3 {
		return fmt.Errorf("expected a committed snapshot and 3 rows, got %d rows", output.NumRows())
	}
	fmt.Printf("Read %d rows from taxi.trips and verified a committed snapshot.\n", output.NumRows())
	return nil
}

func main() {
	if err := run(context.Background()); err != nil {
		log.Fatal(err)
	}
}

Run the program:

go mod tidy
go run .

Read 3 rows from taxi.trips and verified a committed snapshot.

The append returns a new table handle with the committed snapshot. The scan uses that handle to read the rows back.

Configuration

This page documents how to configure Apache Iceberg Go: the CLI's YAML config file, per-catalog Option surfaces, file-system credentials, table write properties, concurrency, and how to plug in custom catalogs and IO backends.

Only properties and options that the iceberg-go code actually reads are listed. Properties defined in the Apache Iceberg spec but not yet wired into iceberg-go are intentionally omitted - check pkg.go.dev/github.com/apache/iceberg-go for the latest read sites.

CLI configuration file

The iceberg CLI loads catalog defaults from ~/.iceberg-go.yaml (override the directory with GOICEBERG_HOME). The schema, defined in config/config.go, is:

default-catalog: default
max-workers: 5
catalog:
  default:
    type: rest
    uri: https://example.com/iceberg
    warehouse: s3://my-bucket/warehouse
    credential: <client-id>:<client-secret>
    output: text
    aws-profile: ""
    rest:
      sigv4-enabled: false
      signing-name: ""
      signing-region: ""
KeyPurpose
default-catalogName used when --catalog-name is not passed on the CLI.
max-workersWorker pool size for concurrent operations. Default 5.
catalog.<name>.typeOne of rest, hive, glue, sql, hadoop, dynamodb.
catalog.<name>.uriCatalog endpoint or DSN.
catalog.<name>.warehouseWarehouse identifier (REST/Glue) or location (Hive/SQL).
catalog.<name>.credentialCredential string passed through to the catalog's auth handler.
catalog.<name>.outputCLI output format (e.g. text, json).

Catalog options

Each catalog package exposes its own functional Option set. The lists below reflect the public option surface; pkg.go.dev is authoritative for the current set.

REST (catalog/rest)

The most option-rich surface. Source: catalog/rest/options.go.

When GET /v1/config returns a non-null idempotency-key-lifetime, the client sends fresh UUIDv7 Idempotency-Key headers on namespace, table, view and transaction mutations, including create view, and on scan cancellation. After negotiation, a configured default Idempotency-Key is dropped from all requests when the server advertises a lifetime; the initial GET /v1/config may still carry it because advertisement is not yet known. Scan plan and task requests send keys independently of this advertisement and have a separate retry policy. Go's standard HTTP transport may replay certain failed requests on reused connections with the same key. The advertised lifetime is not currently enforced, including zero or malformed values.

AWS SigV4 is an optional backend. catalog/rest no longer links the AWS SDK. To sign REST requests with SigV4, pull in the catalog/rest/sigv4 sub-package one of two ways:

  • Property or ambient credentials: add a blank import _ "github.com/apache/iceberg-go/catalog/rest/sigv4" and enable signing with WithSigV4 / WithSigV4RegionSvc or the rest.sigv4-enabled property. The backend signs with the s3.* credential properties when set (falling back to the rest.* aliases), otherwise with the AWS default credential chain.
  • Explicit config: pass sigv4.WithAWSConfig(cfg) to NewCatalog alongside WithSigV4 / WithSigV4RegionSvc (no blank import needed). It supplies the aws.Config; the signing service comes from those options (or a server /v1/config override), and so does the region when one is set. Otherwise the region falls back to cfg.Region.

The former rest.WithAwsConfig(aws.Config) has been removed in favor of these paths. Because signing is enabled by WithSigV4 / WithSigV4RegionSvc (or the rest.sigv4-enabled property) rather than by supplying a config, a program that loads a REST catalog with rest.sigv4-enabled=true now fails at startup until the catalog/rest/sigv4 backend is blank-imported; the error names the import to add.

Conditional table loads

When a load returns an ETag, the REST catalog caches the response and sends If-None-Match on subsequent loads of the same table in the same snapshot loading mode. On a 304 response, it builds the table from the cached response. The expiry interval starts when the response is cached.

PropertyDefaultMeaning
rest-table-cache.max-entries100Maximum cached table responses. Use 0 to disable the cache.
rest-table-cache.expire-after-write-ms300000Time a cached response can be reused, in milliseconds.

The default User-Agent has the form iceberg-go/<version> (go <version>). Set User-Agent with WithHeaders to override it.

Authentication type

The rest.auth.type property selects how the client authenticates, as in Iceberg Java. It is read only from the properties the client supplies; a server's /v1/config defaults and overrides can't change it. An AuthManager passed with WithAuthManager takes precedence over it.

ValueBehavior
unset or oauth2Use token, or the client-credentials flow with credential. With neither, send no authorization header.
noneSend no authorization header, even if token or credential is set.
basicHTTP Basic authentication with rest.auth.basic.username and rest.auth.basic.password, both required. Like rest.auth.type, they are read only from the client's properties.
sigv4Sign every request with AWS SigV4 and authenticate with the type in rest.auth.sigv4.delegate-auth-type (default oauth2; sigv4 is rejected). Requires a blank import of catalog/rest/sigv4. Unlike rest.sigv4-enabled, a server override can't turn this signing off.
googleGoogle credentials, for catalogs such as BigLake. Requires a blank import of catalog/rest/googleauth.

Other values select an auth manager registered with rest.RegisterAuthManager. An unregistered value fails NewCatalog / catalog.Load.

When SigV4 signs a request that already carries an Authorization header, such as the oauth2 or basic header of the delegate auth type, the header moves to Original-Authorization and is signed with the request, as in Java. This also applies to rest.sigv4-enabled.

Google BigLake

With rest.auth.type=google, the catalog/rest/googleauth backend authenticates with Google credentials, using the same properties as Java's GoogleAuthManager:

PropertyDescription
gcp.auth.credentials-pathPath to a credentials JSON file, such as a service account key.
gcp.auth.credentials-jsonThe same JSON, inline. Setting both is an error.
gcp.auth.scopesComma-separated OAuth scopes. Default https://www.googleapis.com/auth/cloud-platform.

Without either credentials property, Application Default Credentials are used. Like rest.auth.type, these are read only from the client's properties.

Token requests don't go through the catalog's HTTP client, so a transport, TLS config or proxy set with WithCustomTransport, WithTLSConfig or WithTransportFactory doesn't apply to them, as in Java. They use a client with the default transport and a 60-second timeout. To use a specific client, put it in the context's oauth2.HTTPClient value when loading the catalog, or build the token source yourself (for example with googleauth.TokenSource) and pass NewOAuth2AuthManager(ts) to WithAuthManager. One exception: on Google Cloud compute, Application Default Credentials come from the metadata server, which the Google library always reaches through its own client.

import (
	"github.com/apache/iceberg-go"
	"github.com/apache/iceberg-go/catalog"
	_ "github.com/apache/iceberg-go/catalog/rest/googleauth"
)

cat, err := catalog.Load(ctx, "biglake", iceberg.Properties{
	"type":                       "rest",
	"uri":                        "https://biglake.googleapis.com/iceberg/v1/restcatalog",
	"warehouse":                  "gs://lakehouse-public-data",
	"rest.auth.type":             "google",
	"header.x-goog-user-project": "my-project",
})

Custom token sources

WithCredential uses the OAuth2 client-credentials flow against the catalog's token endpoint. For other identity providers, wrap any oauth2.TokenSource with NewOAuth2AuthManager and pass it to WithAuthManager. The Google setup above can also be written this way:

ts, err := google.DefaultTokenSource(ctx, "https://www.googleapis.com/auth/cloud-platform")
if err != nil {
	return err
}
cat, err := rest.NewCatalog(ctx, "biglake", "https://biglake.googleapis.com/iceberg/v1/restcatalog",
	rest.WithAuthManager(rest.NewOAuth2AuthManager(ts)),
	rest.WithWarehouseLocation("gs://lakehouse-public-data"),
	rest.WithHeaders(map[string]string{"x-goog-user-project": "my-project"}))

The manager reuses a token until it expires, then asks the source for a new one. That refresh runs on the HTTP client the source was built with. For google.DefaultTokenSource that is the client in the context's oauth2.HTTPClient value, or http.DefaultClient, which has no timeout. With rest.auth.type=google, the backend sets a client with a 60-second timeout unless the context already carries one.

Metrics reporting

The REST catalog can POST scan and commit metrics to the catalog's .../tables/{table}/metrics endpoint. These properties are passed as client-supplied catalog properties.

PropertyDescription
rest-metrics-reporting-enabledOpt into POSTing metrics reports. Off by default.
rest.metrics-reporting-enabledLegacy dotted alias; consulted only when the canonical key above is absent.
rest-metrics-reporting-timeout-msPer-report request/response deadline in milliseconds. Default 10000.

Note on cross-client parity. Iceberg Java defaults metrics reporting to on (METRICS_REPORTING_ENABLED_DEFAULT=true); iceberg-go deliberately defaults it off, so no client emits new outbound telemetry unless it explicitly opts in. A Java client that never set the flag will therefore stop reporting when ported here until rest-metrics-reporting-enabled=true is set. Enablement is read from client properties only — a server cannot turn on reporting the client never asked for — but an explicit server override setting the flag to false is honored (disabling is always safe), so an operator can suppress reporting fleet-wide. rest-metrics-reporting-timeout-ms is a Go-specific extension with no Java, PyIceberg, or Rust equivalent; do not assume parity on it in multi-client deployments.

File-system credentials

iceberg-go registers the local file system (file://) automatically. Cloud schemes are not registered until you add a blank import:

import _ "github.com/apache/iceberg-go/io/gocloud/s3"    // s3, s3a, s3n, oss
import _ "github.com/apache/iceberg-go/io/gocloud/gcs"   // gs
import _ "github.com/apache/iceberg-go/io/gocloud/azure" // abfs, abfss, wasb, wasbs

Each backend package links its own cloud SDK. Importing io/gocloud registers all three at once and links all cloud SDKs.

Without a matching blank import, these schemes return ErrIOSchemeNotFound with a hint naming the package to import.

All credential and tuning property keys are constants in io/config.go. They can be supplied through table properties, catalog properties, or per-call iceberg.Properties arguments depending on context.

S3

When remote signing is disabled, authentication is resolved in this order (io/gocloud/s3/s3.go):

  1. Static credentials in properties: s3.access-key-id + s3.secret-access-key (+ optional s3.session-token).
  2. The standard AWS SDK v2 default credential chain - environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN), ~/.aws/credentials, container/IAM role.

With remote signing enabled, S3 uses anonymous SDK credentials and obtains each request's signature from the signing service. No local AWS credentials are needed. REST catalogs use the table's /sign endpoint by default and pass through the response's remote-signing-config headers and properties. When that config is present, legacy signer.endpoint, signer.uri, and s3.signer.uri settings are ignored. rest.remote-signing.endpoint can explicitly override the default. It may be an absolute URL or a path relative to the catalog URI. Legacy settings are supported when the response has no remote signing config.

A table-specific token takes precedence over the catalog token. The catalog's refreshing authentication is reused only when the signer shares the catalog's origin. For a separate signing service, use the headers supplied in remote-signing-config or a table-specific token. For a standalone S3 FileIO, set s3.signer.uri, s3.region, and an optional token for the signing service. When also supplying rest.remote-signing.config, set rest.remote-signing.endpoint to the complete signing endpoint instead.

Object uploads use unsigned payloads. Only bulk-delete XML bodies are sent to the signer. Streaming signatures (aws-chunked) are unsupported. Caller-supplied checksum values are preserved; an upload that sets ChecksumAlgorithm must also supply its checksum value. Signing requests use the caller's context and a 30-second timeout unless the HTTP client has a configured timeout. Remote signing accepts a standard *http.Client or the AWS SDK's buildable client for S3 requests so redirects can be disabled. Other custom HTTP clients are rejected. S3 requests must resolve to SigV4; SigV4a and S3 Express signing are not supported.

Azure Data Lake Storage / Blob

Authentication is selected in the following order (io/gocloud/azure/azure.go); the first applicable option wins, and if none of 1-5 apply the default credential chain (6) is used:

  1. Shared key: a nonempty adls.auth.shared-key.account.name selects this path and requires a nonempty adls.auth.shared-key.account.key.
  2. Per-host SAS token: adls.sas-token.<hostname>, where <hostname> exactly matches the storage account hostname (for example, myaccount.dfs.core.windows.net).
  3. Per-account connection string: adls.connection-string.<account-name> (for example, adls.connection-string.myaccount).
  4. Static access token: a nonempty adls.token, supplied without the Bearer prefix.
  5. Managed identity: adls.auth.managed-identity.enabled set to exactly "true" selects this path and uses ManagedIdentityCredential directly. Set adls.client-id to select a user-assigned managed identity; otherwise, the system-assigned managed identity is used.
  6. Default credential chain: DefaultAzureCredential, which includes managed identity among its credential sources.

adls.token accepts an OAuth2 access token for Azure Storage, including a token supplied by a catalog. An empty value is ignored. A rejected or expired token does not fall back to managed identity or the default credential chain.

The token is static and is not refreshed. As in Java and PyIceberg, the credential reports a one-hour cache window to the Azure SDK each time the SDK requests the token. This does not extend the token's actual validity: Azure enforces its expiration. Callers must obtain a new token and recreate the FileIO when it expires; changing the original properties map does not update an existing FileIO.

A REST catalog can also vend adls.token as a storage credential. The token carries no expiry of its own, so a vended token's expiry comes from expiration-time in the same credential when the catalog supplies one. Without it, a table FileIO that can fetch new credentials assumes a 60-minute lifetime and renews them shortly before it ends, and one that cannot, such as a FileIO for a scan plan's credentials, treats them as never expiring. A token whose actual lifetime is shorter than that fails with authorization errors until it is renewed, so catalogs that vend adls.token should send expiration-time with it. For the storage account it is vended for, a vended token replaces the SAS token and connection string configured for that account and any shared key, which would otherwise take precedence over it; a shared key is not scoped to an account, so one configured for another account would be used for this account too. The SAS tokens and connection strings of other accounts are kept. Expiries configured for other credentials, such as a SAS expiry or an expiration-time in the catalog or table configuration, do not affect when the token is renewed.

Note on cross-client parity. The two properties in step 5 diverge from the other clients. adls.auth.managed-identity.enabled is Go-specific: neither Iceberg Java nor PyIceberg defines a property that forces ManagedIdentityCredential, so catalog properties that set it do not carry over. adls.client-id collides in name only — PyIceberg reads it as a service principal client ID used together with adls.client-secret and adls.tenant-id, neither of which iceberg-go defines (see the PyIceberg ADLS configuration), while Java's AzureProperties defines no adls.client-id at all. Here it is only ever read as a user-assigned managed identity ID, and only when step 5 is selected.

Pluggability

Two registries are user-extensible. The third (LocationProvider) is currently informational.

IO scheme registry

Register a custom URL scheme from an init function with io.MustRegister:

import (
    "context"
    "net/url"

    "github.com/apache/iceberg-go/io"
)

func init() {
    io.MustRegister("myfs", func(ctx context.Context, parsed *url.URL, props map[string]string) (io.IO, error) {
        return newMyFS(parsed, props)
    })
}

io.Register and io.MustRegister both panic for invalid or duplicate global schemes, preserving the existing registration contract. registry.Register on an independent registry returns ErrInvalidSchemeFactory or ErrSchemeAlreadyRegistered instead. Built-in schemes: file, "" (the empty scheme). Cloud schemes (s3, gs, abfs, etc.) are registered only when the matching backend package under io/gocloud is blank-imported.

io.GetRegisteredSchemes() returns the current scheme list; io.Unregister(scheme) removes one.

To register schemes at runtime without changing other users of the same process, create an independent registry:

registry := io.NewRegistry()
if err := registry.Register("myfs", myFactory); err != nil {
    return err
}
fs, err := registry.LoadFS(ctx, props, "myfs://bucket/key")

io.NewRegistry() copies schemes already registered globally (including blank-imported cloud backends) but keeps later registrations independent. registry.Clone() makes an isolated copy of another registry. registry.Names() lists the schemes registered in that instance. registry.LoadFSFunc() is the lazy factory equivalent. Global io.LoadFS() and io.LoadFSFunc() continue using the default registry.

Pass the catalog's WithIORegistry(registry) option to NewCatalog in Glue, Hadoop, Hive, REST, or SQL. For direct view metadata creation or writes, pass view.WithIORegistry(registry) to the view helper. Omitting the option or passing nil uses the global registry. An empty non-nil registry has no registered schemes. A catalog-scoped registry does not affect catalog.Load, which uses the global registry with the built-in catalog registrars.

The catalog holds the supplied registry, so registering or unregistering a scheme affects future FileIO resolutions. Hadoop opens its warehouse filesystem during construction and reuses it for warehouse operations. Use registry.Clone() to give another catalog its own set of schemes.

View metadata creation accepts the same scoped registry option, but reading view metadata via view.NewFromLocation uses the filesystem factory explicitly passed by the caller. A catalog's own load and update methods supply their scoped factory. Passing credentials in ioProps configures the filesystem; only metadataProps are persisted in the view metadata.

These FileIO options do not select a KMS implementation. encryption.KMSRegistry is separate; no catalog encryption path currently loads a KMS client.

import (

By default files reads the manifest list and manifests itself and prints them as a tree: snapshot, manifest, then each manifest entry.

Automation

Two flags make these commands safe to run from cron jobs or CI:

  • --yes skips the interactive prompt. Without it in a non-interactive environment, the CLI exits with stdin is not a terminal: use --yes to confirm in non-interactive mode rather than hanging.
  • --output json emits structured output that can be consumed by jq and downstream tooling.

Daily maintenance over every table in a namespace:

#!/bin/bash
TABLES=$(iceberg list my_db --output json | jq -r '.identifiers[].name')
for table in $TABLES; do
  iceberg expire-snapshots --older-than 7d --retain-last 3 --yes \
    --output json "my_db.$table"
  iceberg clean-orphan-files --older-than 3d --yes \
    --output json "my_db.$table"
done

Tag tables before a deploy:

iceberg tag create --yes my_db.events "pre-deploy-$VERSION"
iceberg tag create --yes my_db.users  "pre-deploy-$VERSION"

Audit-only report (no commits):

iceberg expire-snapshots --older-than 7d --dry-run --output json my_db.events \
  | jq '{table, would_expire: .expired_snapshot_count}'

Safety features

Every write command has multiple layers of protection:

  • --dry-run — shows the would-be effect without committing. Look for [DRY RUN] in text output or "dry_run": true in JSON.
  • --yes — required to skip the prompt; without it, non-interactive shells get an explicit error rather than hanging.
  • TTY detection — interactive prompts are only shown when stdout is a terminal.
  • Ancestor validation — rollback rejects target snapshots that are not in the current branch's history.
  • Version check — upgrade refuses same-version or downgrade requests.

Reading data

(t Table) Scan(opts ...ScanOption) *Scan returns a scan that you can resolve into Arrow data.

Parquet and Avro data files are readable. Avro scan tasks must cover the whole file. The reader decodes the file before projecting columns, and supports nullable unions with null and one value type.

Streaming record batches

import "github.com/apache/iceberg-go/table"

scan := tbl.Scan()
arrowSchema, batches, err := scan.ToArrowRecords(ctx)
if err != nil { /* ... */ }

fmt.Println(arrowSchema)
for batch, err := range batches {
    if err != nil { /* ... */ }
    fmt.Printf("batch with %d rows\n", batch.NumRows())

}

Incremental changelog scans

NewIncrementalChangelogScan returns rows added or deleted between snapshots. PlanFiles returns the tasks. Read reads a planned task list, and ToArrowRecords plans and reads. Remote planning is not supported.

schema, batches, err := tbl.NewIncrementalChangelogScan(
    table.WithSelectedFields("id", "name"),
).FromSnapshotExclusive(startSnapshotID).ToArrowRecords(ctx)

FromSnapshotInclusive, FromSnapshotExclusive, and ToSnapshot bound the snapshot range. Projection, row filters, and limits apply while the rows are read. If the start snapshot has been expired, changes in expired snapshots before the oldest retained one are not reported. Each snapshot that adds deletes is planned against every live data file, narrowed only by the partition filter, so the cost follows the table size rather than the size of the snapshot range.

Each batch is the scan projection followed by three columns:

  • _change_type — INSERT or DELETE
  • _change_ordinal — int32 ordinal of the snapshot that produced the change
  • _commit_snapshot_id — snapshot ID that committed the change

Added data files are inserts. Removed data files are deletes of the rows in that file. Delete files added in the range emit the rows they newly remove. A rewritten file emits a DELETE and an INSERT for every row in that file, including rows that did not change. UPDATE rows are not produced. Delete-file handling is iceberg-go behavior.

Use ToNormalizedArrowRecords to remove matching DELETE/INSERT occurrences of unchanged rows within each snapshot. Set ComputeUpdates to label remaining rows with the same identifier as UPDATE_BEFORE and UPDATE_AFTER:

schema, batches, err := tbl.NewIncrementalChangelogScan(
    table.WithSelectedFields("id", "name"),
).FromSnapshotExclusive(startSnapshotID).ToNormalizedArrowRecords(ctx,
    table.ChangelogNormalizationOptions{
        ComputeUpdates:   true,
        IdentifierFields: []string{"id"},
    })

The zero options value only removes carryovers. Update images use IdentifierFields, or the effective schema's identifier fields when the list is empty. Explicit identifiers may be nullable primitive columns, including paths through structs, and follow the scan's case sensitivity. After removing carryovers, an identifier must have at most one DELETE and one INSERT per snapshot. Duplicate identifiers return an error instead of selecting an ambiguous update image.

Normalization compares complete rows before applying row filters, projection, and the output limit. Row-lineage columns do not affect matching. Variant values are compared by their encoded metadata/value bytes, with physical NULL distinct from an encoded Variant null. Changes from different snapshots are kept separate. Output follows snapshot and source-task order, with each UPDATE_AFTER immediately following its UPDATE_BEFORE. A batch boundary or row limit may split the pair. Callers release each returned batch.

The reader buffers one snapshot at a time. MaxBufferedBytes defaults to 64 MiB of retained Arrow buffers and encoded matching keys, and MaxBufferedRows defaults to 1,000,000 input rows per snapshot. Exceeding either limit returns ErrChangelogBufferLimit through the iterator before emitting that snapshot. Decoding, temporary key encoding, output batches, and per-row indexes need additional memory. Temporary keys are individually capped at MaxBufferedBytes. WithArrowBatchSize also caps output batch rows; the default output batch size is 4096.

Writing data

The shortcut methods on Table open a transaction, perform the write, and commit. Use NewTransaction directly when you need to combine multiple operations.

Append

import (
    "github.com/apache/arrow-go/v18/arrow/array"
)

// From a streaming RecordReader
newTbl, err := tbl.Append(ctx, recordReader, nil /* snapshot props */)

// From an in-memory Arrow Table; batchSize controls the rolling writer
newTbl, err = tbl.AppendTable(ctx, arrowTbl, 1024, nil)

Overwrite

import "github.com/apache/iceberg-go/table"

// Replace all data
newTbl, err := tbl.Overwrite(ctx, recordReader, nil)

// Replace only rows matching a filter
newTbl, err = tbl.Overwrite(ctx, recordReader, nil,
    table.WithOverwriteFilter(
        iceberg.EqualTo(iceberg.Reference("date"), "2026-01-01"),
    ),
)

OverwriteTable is the arrow.Table variant.

Dynamic partition overwrite

Replace only the partitions present in the incoming data. Unlike a filtered row-level overwrite, this removes all existing data files in those partitions while retaining files in other partitions.

// Write Arrow record batches, replacing only partitions receiving new rows.
newTbl, err := tbl.DynamicPartitionOverwrite(ctx, recordReader, nil)

// In-memory Arrow tables work too.
newTbl, err = tbl.DynamicPartitionOverwriteTable(ctx, arrowTbl, 1024, nil)

// Or commit already-written Iceberg DataFile metadata through a transaction.
txn := tbl.NewTransaction()
err = txn.DynamicPartitionOverwriteDataFiles(ctx, newDataFiles, nil)
if err == nil {
    newTbl, err = txn.Commit(ctx)
}

This supports Iceberg format v1-v3. Incoming files must use the current partition spec. On partitioned tables, files under older specs are preserved; only matching current-spec partitions are replaced. If the current spec is unpartitioned, non-empty input replaces all live files, including files under older specs. For v3, replacement also removes deletion vectors tied to replaced data files. Empty input leaves the table untouched.

A concurrent add or removal in a replaced partition fails validation, while independent changes to other partitions can be retried after a catalog refresh. A new target branch also pins the source branch to prevent missing concurrent writes. Default partition-spec and sort-order changes fail validation. Written data files are not automatically cleaned up if staging or commit fails, so callers must handle those files before retrying with a new transaction.

Delete

newTbl, err := tbl.Delete(ctx,
    iceberg.LessThan(iceberg.Reference("id"), int64(100)),
    nil, /* snapshot props */
)

Add existing files

When you already have data files (e.g. produced by another writer), register them without rewriting:

txn := tbl.NewTransaction()
err := txn.AddDataFilesByPath(ctx, []string{
    "s3://my-bucket/sales/orders/data/file-1.parquet",
    "s3://my-bucket/sales/orders/data/file-2.parquet",
}, nil /* snapshot props */, false /* ignoreDuplicates */)
if err != nil { /* ... */ }

newTbl, err := txn.Commit(ctx)

For bucket-partitioned Parquet files, provide each file's partition tuple with WithAddDataFilesByPathPartitionValues. Key the values by file path and partition field ID. Supply every non-void partition field, and make sure the values describe every row in the file.

ReplaceDataFilesByPath(ctx, filesToDelete, filesToAdd, snapshotProps) performs an overwrite of existing files. It is suitable when the logical table data changes. ReplaceDataFiles(ctx, filesToDelete, dataFilesToAdd, snapshotProps, opts...) is the corresponding data-file metadata API.

Stage externally rewritten Parquet files

When another engine has already written replacement Parquet files with the same live rows and physical record count, use StageRewrittenDataFilesByPath. This stages an Iceberg replace snapshot instead of an overwrite, but it does not read or rewrite the row data:

txn := tbl.NewTransaction()
err := txn.StageRewrittenDataFilesByPath(ctx, oldFilePaths, newFilePaths, nil)
if err != nil { /* ... */ }
newTbl, err := txn.Commit(ctx)

This path-only helper supports unpartitioned format v1 and v2 tables. It rejects a source file with any applicable position or equality deletes, as well as deletion vectors. It requires the same total physical record count and checks column value, null, and NaN counts when available for every file on both sides. Missing optional statistics are unknown, not zero. A source column with known value counts cannot disappear when replacement metrics collection is enabled. Footer metadata cannot prove row-level equivalence, so callers must preserve every live row. Format v3 and partitioned tables are not supported, including older partitioned specs that are no longer current.

For compaction that must apply deletes, remove delete files, or rewrite partitioned data, use RewriteDataFiles. An external writer that needs to supply data-file metadata, a sequence number, or related delete-file changes can use NewRewrite with FileToDataFile instead.

Transactions

Group writes and metadata changes into one atomic snapshot:

txn := tbl.NewTransaction()

if err := txn.Delete(ctx,
    iceberg.LessThan(iceberg.Reference("date"), "2026-01-01"), nil); err != nil {
    /* ... */
}
if err := txn.Append(ctx, recordReader, nil); err != nil {
    /* ... */
}
if err := txn.SetProperties(iceberg.Properties{"commit.user": "data-pipeline"}); err != nil {
    /* ... */
}

newTbl, err := txn.Commit(ctx)

To target a specific branch:

txn, err := tbl.NewTransactionOnBranch("staging")
if err != nil { /* ... */ }

Cherry-pick an existing snapshot onto the transaction's target branch:

err := txn.CherryPickSnapshot(ctx, sourceSnapshotID, nil)
if err != nil { /* ... */ }
newTbl, err := txn.Commit(ctx)

A direct-child source fast-forwards without copying data and ignores snapshotProps. A divergent v1/v2 append is replayed with fresh snapshot metadata; user-supplied WAP publication markers are not trusted. Divergent v3 appends and divergent replace-partitions overwrites are tracked in issue #2415. Cherry-picks pin the refs they rely on. Divergent replays onto new branches also pin main; fast-forwards onto new branches do not. A moved pinned ref fails the commit; other conflicts can be retried under the normal commit retry policy.

Commit retries a conflict (ErrCommitFailed) up to commit.retry.num-retries times, 4 by default. See Automatic retry for the commit.retry.* table properties.

txn.SetLocation(location) stages a new table base location in the same storage scheme and authority, including the bucket or container where applicable. Existing files keep their paths. New writes use the staged base and honor explicit write-path properties. Commit the transaction to publish the change.

Schema and partition evolution

Schema evolution

import "github.com/apache/iceberg-go/table"

txn := tbl.NewTransaction()

err := table.NewUpdateSchema(txn, true /* caseSensitive */, false /* allowIncompatibleChanges */).
    AddColumn([]string{"tip"}, iceberg.PrimitiveTypes.Float64, "Tip in dollars", false, nil).
    RenameColumn([]string{"name"}, "full_name").
    DeleteColumn([]string{"deprecated_field"}).
    Commit()
if err != nil { /* ... */ }

newTbl, err := txn.Commit(ctx)

Reorder fields with MoveFirst, MoveBefore, or MoveAfter. Set allowIncompatibleChanges to true to permit type narrowing or making optional columns required.

Partition evolution

us := table.NewUpdateSpec(txn, true /* caseSensitive */)
us.AddField("event_time", iceberg.DayTransform{}, "event_day") // sourceColName, transform, partitionFieldName
us.RemoveField("legacy_partition")
if err := us.Commit(); err != nil { /* ... */ }

AddField chains; AddIdentity(sourceCol) is a shortcut for an identity transform; RenameField(name, newName) renames an existing partition field.

Available transforms (root iceberg package): IdentityTransform{}, YearTransform{}, MonthTransform{}, DayTransform{}, HourTransform{}, BucketTransform{NumBuckets: N}, TruncateTransform{Width: W}.

Sort order evolution

Use the transaction builder to replace the full default sort order. It binds column names against the transaction's staged schema. An empty builder resets the order to unsorted:

txn := tbl.NewTransaction()
builder := txn.NewReplaceSortOrder(true).
    Asc("event_time", table.NullsLast).
    AddField("user_id", iceberg.BucketTransform{NumBuckets: 16}, table.SortASC, table.NullsFirst)
if err := builder.Commit(); err != nil { /* ... */ }

newTbl, err := txn.Commit(ctx)

Call Transaction.ReplaceSortOrder directly when you already have a table.SortOrder, such as one built from field IDs:

order, err := table.NewSortOrder(1, []table.SortField{{
    SourceIDs: []int{1}, Transform: iceberg.IdentityTransform{},
    Direction: table.SortASC, NullOrder: table.NullsFirst,
}})
if err != nil { /* ... */ }
if err := txn.ReplaceSortOrder(order); err != nil { /* ... */ }

Replacing the default sort order affects future writes; it does not rewrite existing data files. To physically reorder existing data, run a separate sort compaction.

The Go writers currently support only top-level sort columns. A nested-field order can be registered, as in Java, but a later append fails until the default order is replaced.

Use SortOrder.Satisfies(required) to compare sort metadata using Iceberg's transform ordering rules.

Comparing physical files between snapshots (v1-v3)

Use tbl.DiffSnapshotFiles to compare the live content files referenced by two snapshot IDs, including snapshots on different branches:

Branches and tags

To create a branch or tag at an existing snapshot, use branch create or tag create in the CLI. In Go, call Catalog.CommitTable with table.NewSetSnapshotRefUpdate to choose the starting snapshot and any retention settings. This example uses the table's current snapshot:

import "github.com/apache/iceberg-go/table"

snap := tbl.CurrentSnapshot()
update := table.NewSetSnapshotRefUpdate(
    "audit",                  // ref name
    snap.SnapshotID,
    table.BranchRef,          // or table.TagRef
    0,                        // maxRefAgeMs (0 = unset)
    0,                        // maxSnapshotAgeMs (0 = unset)
    0,                        // minSnapshotsToKeep (0 = unset)
)
reqs := []table.Requirement{
    table.AssertTableUUID(tbl.Metadata().TableUUID()),
    table.AssertRefSnapshotID("audit", nil), // ref must not already exist
}

_, _, err := cat.CommitTable(ctx, tbl.Identifier(), reqs, []table.Update{update})

To create a branch with its first append, target it with tbl.NewTransactionOnBranch. The append starts from main if the branch is missing and creates the branch on commit. An append to an existing branch builds on that branch's head:

txn, err := tbl.NewTransactionOnBranch("audit")
if err != nil { /* ... */ }
if err := txn.AppendTable(ctx, arrowTbl, 1024, nil); err != nil { /* ... */ }
updated, err := txn.Commit(ctx)

See reading from a branch or tag to scan the updated ref.

Branch promotion and replacement

Use a transaction to advance a branch to another branch or tag, or to move it to an existing snapshot. Fast-forward checks that the target's current snapshot is an ancestor of the source. It creates the target when missing, while ReplaceBranch requires an existing target branch.

txn, err := tbl.NewTransactionOnBranch("main")
if err != nil { /* ... */ }
if err := txn.FastForwardBranch("main", "audit"); err != nil { /* ... */ }
updated, err := txn.Commit(ctx)

// Without ancestry checks (can move a branch backwards or across histories):
txn, err = updated.NewTransactionOnBranch("main")
if err != nil { /* ... */ }
err = txn.ReplaceBranch("main", snapshotID)
// Or use ReplaceBranchFromRef("main", "audit"), which can create a missing target.

For a non-main target, call tbl.NewTransactionOnBranch(target) rather than tbl.NewTransaction(). The latter uses main as its commit branch, so a concurrent append to main can reject an otherwise independent promotion.

Existing branch retention settings are preserved. Both the target and source snapshot IDs are pinned when promoting from a ref, and the target is pinned when replacing by ID. If the source snapshot was staged in the same transaction, the commit branch is pinned too, preventing retry from changing its ancestry. A pinned ref that moves prevents the normal retry of a co-staged append. A retention-only change with the same snapshot ID cannot be detected by snapshot-ID requirements in any catalog. REST catalogs also cannot detect ref type changes with the same ID.

Fast-forward needs the complete snapshot ancestry. REST catalogs using snapshot-loading-mode=refs can omit intermediate ancestors, causing valid fast-forwards to fail. Load with snapshot-loading-mode=all instead. Replacing by snapshot ID can also fail if the requested historical snapshot was omitted. See Concurrent Writes.

tbl.RenameBranch(ctx, from, to) renames a non-main branch to an unused name and preserves its snapshot and retention settings. Use txn.RenameBranch(from, to) to stage the rename alongside other updates.

// Roll back to a previous snapshot

Snapshot integrity audit (v1 and later)

Use ValidateSnapshot to inspect a snapshot's manifest list and entries without changing table data. This is especially useful for checking imported v1 tables before allowing them into production.

report, err := tbl.ValidateSnapshot(ctx, snapshotID)
if err != nil {
    return err // I/O failed or the scan was canceled; report may be incomplete.
}
if !report.Valid() {
    for _, issue := range report.Issues {
        fmt.Printf("%s: %s (%s)\n", issue.Code, issue.FilePath, issue.ManifestPath)
    }
}

The report checks manifest versions, partition spec references, content types, manifest entry counts, duplicate manifest paths, and duplicate live content files across all manifests in a snapshot. It also checks that live deletion vectors have a target path, that their blob ranges fit within the recorded file size, and that no two distinct vectors target the same data file. Deleted entries do not count as live. A report is valid only when Complete is true and Issues is empty. This is a metadata-only audit: it does not check data-file contents or whether data-file objects still exist. The audit works with both v1 manifest lists and older v1 snapshots containing embedded manifests paths. For embedded manifests, the partition spec ID is checked against table metadata when the optional header provides it, or inferred when the partition fields match exactly one historical spec. Missing, ambiguous, or mismatched partition specs are reported as issues rather than silently accepted.

The file uniqueness and manifest requirements come from the Iceberg spec and manifest list spec.

Maintenance

Partition statistics (v1-v3)

ComputePartitionStatistics writes a Parquet statistics file for the transaction's current branch head and stages its registration. Use a fresh transaction and commit it to publish the reference:

txn := tbl.NewTransaction()
stats, err := txn.ComputePartitionStatistics(ctx)
if err != nil { /* ... */ }
newTbl, err := txn.Commit(ctx)

The operation recomputes statistics from live manifest entries without reading data files, delete-file contents, or Puffin blobs. It groups rows by partition spec ID and partition tuple and sorts by the unified tuple with NULL first. V2 includes position and equality delete metrics. V3 also counts deletion vectors in dv_count; their records contribute to position_delete_record_count, while position_delete_file_count counts classic files only, including V2 files retained after an upgrade.

total_record_count is exact for tables without deletes and for DV-only tables whose live targets, partitions, sequence numbers, and record counts can be validated from metadata. A live classic position or equality delete makes this field NULL for every partition, since deletes may apply across specs. Unknown DV sequence numbers also leave the affected total NULL. Optional last-updated fields are left NULL. PartitionStatisticsSchema exposes the versioned schema; PartitionStatisticsSchemaV1 remains available.

The table must have a snapshot and at least one partition field in its spec history. Dropped partition source fields and changed transform result types are not supported. A concurrent change to the target branch, current schema, or partition layout rejects the commit. Statistics do not create a new snapshot.

Puffin statistics

puffin.Writer.AddBlob accepts BlobMetadataInput.CompressionCodec with CompressionCodecLZ4 or CompressionCodecZstd. puffin.Reader.ReadBlob decodes the stored codec. Write deletion-vector blobs with an empty codec.

tbl.ComputeNDVs(ctx, snapshotID, columns...) scans the selected snapshot and returns estimated distinct counts and serialized Theta sketches keyed by Iceberg field ID. Pass 0 for the current snapshot. Omit the column names to analyze all supported top-level primitive columns in the snapshot schema. Geometry, geography, and unknown types are skipped by default. Explicit column names must refer to supported top-level primitive columns. The estimates exclude null values and empty strings and binary values.

Use table/stats.NewSketch to build a sketch directly from serialized Iceberg single values, and NewUnion to merge compatible sketches. The serialized sketch is the payload for an apache-datasketches-theta-v1 Puffin blob.

After writing a Puffin statistics file, pass its snapshot ID, path, sizes, and blob metadata to txn.SetStatistics. Commit to publish the reference. txn.RemoveStatistics(snapshotID) stages removal of the reference.

Delete-file maintenance

  • RewritePositionDeleteFiles compacts compatible v2 Parquet position-delete files from the current partition spec that have no deleted-row payload.
  • ConvertEqualityDeletesToDeletionVectors rewrites live equality deletes on a v3 table as file-specific deletion vectors.
  • PlanDanglingDeleteFiles identifies whole delete files that apply to no data file in the target snapshot. RemoveDanglingDeleteFiles removes their references on v2 and v3. The physical files remain available to older snapshots that reference them.

The table-level methods operate on main. Use the transaction variants to target another branch or combine changes, then commit the transaction.

Compaction (rewrite data files)

import "github.com/apache/iceberg-go/table"

txn := tbl.NewTransaction()
result, err := txn.RewriteDataFiles(ctx, groups /* []table.CompactionTaskGroup */, table.RewriteDataFilesOptions{})
if err != nil { /* ... */ }

newTbl, err := txn.Commit(ctx)
fmt.Printf("rewrote %d files into %d (%d -> %d bytes)\n",
    result.RemovedDataFiles, result.AddedDataFiles, result.BytesBefore, result.BytesAfter)

The table/compaction subpackage provides bin-packing planning. The iceberg compact analyze and compact run CLI commands wrap the same machinery - see CLI.

Compaction tasks represent complete data files, not independent scan splits. The planner collapses split tasks for the same file into one whole-file task, rejecting inconsistent delete or lineage metadata and dropping residual filters because they select files but do not filter rows during compaction. Direct calls to ExecuteCompactionGroup reject partial ranges and residual row filters. Attached delete files are still applied when rewriting each source file.

To sort instead of bin-pack, pass table.WithCompactionSortOrder as a group option. Each group is sorted as a whole, so every output file holds a sorted, non-overlapping range of it. Output files record the order's sort_order_id when the order is one of the table's sort orders, every field has one source column, every field but the last is identity and the last preserves order (see table.WithCompactionSortOrder). Files of different groups still overlap, and by default a group is packed to one target file, so raise compaction.Config.MaxGroupSizeBytes until a group covers a partition. Set compaction.Config.RewriteAll to also rewrite files that are already well-sized:

cfg := compaction.DefaultConfig()
cfg.RewriteAll = true
cfg.MaxGroupSizeBytes = 8 << 30 // 8 GiB per group
plan, err := compaction.Analyze(ctx, tbl, cfg)
if err != nil { /* ... */ }

result, err := txn.RewriteDataFiles(ctx, groups /* from plan.Groups */, table.RewriteDataFilesOptions{
    GroupOptions: []table.CompactionGroupOption{table.WithCompactionSortOrder(tbl.SortOrder())},
})

When every file of a group already records the order's sort_order_id (for example, files written by an earlier sort rewrite), every sort field is identity, and no partition of the group has more files than the scan concurrency (table.WithCompactionScanConcurrency, GOMAXPROCS by default), the files are streamed and merged, holding up to about five batches per file instead of the whole group. Otherwise a sort rewrite holds each group decoded in memory, and with the batches queued for the writer that can reach about twice the group's decoded size, so keep compaction.Config.MaxGroupSizeBytes within what one rewrite can hold. The first sort rewrite of a table always takes this in-memory path, since its files do not record the order yet. The CLI equivalent is iceberg compact run --sort [--rewrite-all] [--max-group-size BYTES], which uses the table's default sort order.

To cluster spatially instead, pass table.WithCompactionGeometryHilbertOrder with the name of a top-level geometry or geography column. Each partition of a group is ordered along a Hilbert curve over the centre of every geometry's XY bounding box, snapped to a grid of 2^bits cells per axis (table.WithHilbertBits, 16 by default) over the extent of the data (table.WithHilbertBounds fixes the extent). Rows close in space tend to share the same file and row group, so per-file geometry bounds overlap little and spatial filters prune files. Rows with no location (a null or empty geometry) go last. Geography is accepted but ordered on planar x/y, with no antimeridian wrapping. This is not the multi-column hilbert(c1, c2) sort order of Java's rewrite procedure; it orders one geometry column by location. A Hilbert rewrite always holds the whole group decoded in memory, so keep compaction.Config.MaxGroupSizeBytes within what one rewrite can hold. The option cannot be combined with table.WithCompactionSortOrder, and because a Hilbert order is not an Iceberg sort order, output files record no sort_order_id:

result, err := txn.RewriteDataFiles(ctx, groups, table.RewriteDataFilesOptions{
    GroupOptions: []table.CompactionGroupOption{
        table.WithCompactionGeometryHilbertOrder("geom", table.WithHilbertBits(12)),
    },
})

Variant Type

variant is the Iceberg v3 semi-structured type: a single self-describing column that holds arbitrary JSON-like values (objects, arrays, and scalars) without a fixed schema. iceberg-go supports both non-shredded and shredded variants, and can push predicates down into individual variant fields.

Reading and writing

A variant column is declared with iceberg.VariantType{} in the table schema and maps to the Arrow variant extension type (see API). Non-shredded variant values need no extra configuration: write an Arrow record whose variant column uses the extension type, and read it back the same way.

Build the column with a variant builder and write it like any other Arrow column (the table must be format version 3):

import (
    "fmt"

    "github.com/apache/arrow-go/v18/arrow"
    "github.com/apache/arrow-go/v18/arrow/array"
    "github.com/apache/arrow-go/v18/arrow/extensions"
    "github.com/apache/arrow-go/v18/arrow/memory"
    "github.com/apache/arrow-go/v18/parquet/variant"
    "github.com/apache/iceberg-go"
    "github.com/apache/iceberg-go/table"
)

// tbl was created with table.PropertyFormatVersion = "3" and this schema.
schema := iceberg.NewSchema(0,
    iceberg.NestedField{ID: 1, Name: "payload", Type: iceberg.VariantType{}},
)
arrowSchema, _ := table.SchemaToArrowSchema(schema, nil, true, false)

bldr := extensions.NewVariantBuilder(memory.DefaultAllocator, extensions.NewDefaultVariantType())
defer bldr.Release()

var vb variant.Builder
_ = vb.Append(map[string]any{"x": int64(320), "target": "button-submit"})
val, _ := vb.Build()
bldr.Append(val)

col := bldr.NewArray()
defer col.Release()
rec := array.NewRecordBatch(arrowSchema, []arrow.Array{col}, 1)
defer rec.Release()

tx := tbl.NewTransaction()
arrTable := array.NewTableFromRecords(arrowSchema, []arrow.Record{rec})
defer arrTable.Release()
_ = tx.AppendTable(ctx, arrTable, 1024, nil)
tbl, _ = tx.Commit(ctx)

A normal scan reads it back; the variant column comes back as an *extensions.VariantArray:

result, _ := tbl.Scan().ToArrowTable(ctx)
defer result.Release()

variants := result.Column(0).Data().Chunk(0).(*extensions.VariantArray)
v, _ := variants.Value(0)
fmt.Println(v.Value()) // variant.ObjectValue for the object above

Shredding

Shredding stores the fields of a variant as typed Parquet sub-columns instead of a single opaque blob. This lets scans read and filter a field as a native column rather than decoding every value. Shredding is opt-in and configured with two write properties (see Configuration):

  • write.parquet.shred-variants - enable shredding of top-level variant columns (default false).
  • write.parquet.variant-inference-buffer-size - rows buffered per file to infer the shredding schema (default 100).

The reader accepts both shredded and non-shredded data; no read-side configuration is required.

Filtering on variant fields

Filter on a field inside a variant with iceberg.Extract, which plugs into the usual predicate builders. See Row Filter Syntax for usage, supported target types, and caveats.

Casting a primitive variant literal

VariantLiteral.To(typ) converts primitive variant values using the cast rules for the underlying literal. Null, object, array, and zero-value variants return ErrBadCast when cast to a non-variant type.

Constraints

  • A variant column cannot be a partition source or an identity-transform source.

Row Filter Syntax

Row filters drive predicate pushdown during scans, partition pruning, and row-level deletes. The DSL lives in the root iceberg package - all you need is the import:

import "github.com/apache/iceberg-go"

A column is referenced with iceberg.Reference("column_name"). Predicate constructors return a BooleanExpression (or an UnboundPredicate, which satisfies BooleanExpression) that can be combined with the boolean combinators in the Expression DSL and passed to APIs like table.WithRowFilter(...).

Equality

iceberg.EqualTo(iceberg.Reference("status"), "active")
iceberg.NotEqualTo(iceberg.Reference("retries"), int32(0))

EqualTo[T] and NotEqualTo[T] are generic over LiteralType (bool, int32, int64, float32, float64, string, []byte, plus a few iceberg-specific types). The value's type must be in that set - bare int literals are not, so use int32(0) / int64(0) explicitly. They wrap LiteralPredicate(OpEQ, ...) and LiteralPredicate(OpNEQ, ...) (predicates.go:83-91).

Comparison

iceberg.LessThan(iceberg.Reference("amount"), 100.0)
iceberg.LessThanEqual(iceberg.Reference("amount"), 100.0)
iceberg.GreaterThan(iceberg.Reference("created_at"), int64(1700000000))
iceberg.GreaterThanEqual(iceberg.Reference("score"), int32(50))

Operators: OpLT, OpLTEQ, OpGT, OpGTEQ (exprs.go:47-50). Constructors at predicates.go:98-124.

Set membership

iceberg.IsIn(iceberg.Reference("region"), "us-east", "us-west", "eu-west")
iceberg.NotIn(iceberg.Reference("status"), "deleted", "archived")

IsIn and NotIn are variadic. They return a BooleanExpression (not UnboundPredicate) because the result can simplify automatically:

  • Zero values - reduces to AlwaysFalse{} (for IsIn) or AlwaysTrue{} (for NotIn).
  • One value - reduces to EqualTo / NotEqualTo.

See predicates.go:55-78.

Null checks

iceberg.IsNull(iceberg.Reference("deleted_at"))
iceberg.NotNull(iceberg.Reference("user_id"))

These wrap UnaryPredicate(OpIsNull, ...) and UnaryPredicate(OpNotNull, ...). Both panic if the term is nil (predicates.go:23-32).

NaN checks (float / double columns only)

iceberg.IsNaN(iceberg.Reference("ratio"))
iceberg.NotNaN(iceberg.Reference("ratio"))

Operators OpIsNan and OpNotNan. Use these instead of EqualTo(..., math.NaN()) - NaN is never equal to itself, so a comparison or In/NotIn with a NaN literal fails to bind with ErrInvalidArgument.

String prefix

iceberg.StartsWith(iceberg.Reference("path"), "/var/log/")
iceberg.NotStartsWith(iceberg.Reference("name"), "tmp_")

Operators OpStartsWith and OpNotStartsWith (exprs.go:53-54). The value must be a string.

Variant extraction

iceberg.Extract(ref, path, typ) builds a term that navigates a member-selector path into a variant column and casts the leaf to typ. The path uses dot ($.user.age) or quoted-bracket ($['user']['age']) notation; array indexing ($.items[0]), wildcards, filters, and recursive descent are rejected at bind time. It is an UnboundTerm, so it plugs into the same predicate builders as iceberg.Reference:

filter := iceberg.EqualTo(
    iceberg.Extract(iceberg.Reference("payload"), "$.user.age", iceberg.PrimitiveTypes.Int64),
    int64(30),
)

The referenced column must be a variant, and a target type is required. Supported target types: bool, int32, int64, float32, float64, date, time, timestamp, timestamptz, timestamp_ns, timestamptz_ns, string, fixed, binary, decimal, uuid.

Caveats:

  • Extract predicates prune whole data files by shredded-field bounds (best-effort, and only for shredded fields), then filter row by row. Row-group statistics and bloom filters do not apply to them.
  • Extract terms are DSL-only (no string row-filter form) and are not REST-serializable. Under local scan planning (the default) they run as local residuals; with remote scan planning, a filter containing an Extract term fails to serialize rather than being silently dropped.

See Variant Type for shredding.

Expression DSL

This page covers the building blocks behind the row-filter shortcuts in Row Filter Syntax: boolean combinators, terms, and the lower-level predicate constructors.

The DSL lives entirely in the root iceberg package (see exprs.go and predicates.go).

Boolean combinators

iceberg.NewAnd(a, b)              // a AND b
iceberg.NewAnd(a, b, c, d)        // a AND b AND c AND d (variadic)
iceberg.NewOr(a, b)               // a OR b
iceberg.NewOr(a, b, c, d)         // a OR b OR c OR d
iceberg.NewNot(a)                 // NOT a

NewAnd and NewOr accept two required arguments plus a variadic tail (exprs.go:226, exprs.go:287). They simplify automatically:

  • NewAnd(x, AlwaysTrue{}) reduces to x.
  • NewAnd(x, AlwaysFalse{}) reduces to AlwaysFalse{}.
  • NewOr(x, AlwaysFalse{}) reduces to x.
  • NewOr(x, AlwaysTrue{}) reduces to AlwaysTrue{}.
  • NewNot(NewNot(x)) reduces to x.

Constants

iceberg.AlwaysTrue{}
iceberg.AlwaysFalse{}

Both satisfy BooleanExpression. Use them as the identity element when composing filters dynamically.

Terms

A term is the left-hand side of a predicate. Iceberg-go has two flavors:

  • Reference("column_name") - an unbound term that names a column (exprs.go:373). Typing happens at bind time, when the expression is matched against a schema. This is what you almost always want.
  • BoundReference - the resolved form, produced by Reference.Bind(schema, caseSensitive) (exprs.go:389). You only encounter these when writing custom expression visitors.
  • Extract(ref, path, typ) - a variant sub-path term that navigates a member-selector path ($.a.b or $['a']['b']; no array indexing or wildcards) into a variant column and casts the leaf to typ (variant_extract.go). Use it inside any predicate builder to filter on a field within a variant. See Row Filter Syntax.

The interfaces are:

type Term interface { ... }                        // shared marker
type UnboundTerm interface { Term; ... }           // pre-bind
type BoundTerm interface { Term; Ref() BoundReference; ... }

(exprs.go:317-348)

Predicates

A predicate applies an Operation to one or more terms. BooleanExpression is the shared interface (exprs.go:123).

Convenience builders (recommended)

For all the common shapes, the constructors in predicates.go are the right tool. See Row Filter Syntax for the full list (EqualTo, LessThan, IsIn, IsNull, StartsWith, etc.).

Lower-level escape hatches

When the convenience builders are not enough (custom operators, dynamic operation selection, working with already-typed Literal values), use the predicate constructors directly:

// Unary predicates: IS NULL / NOT NULL / IS NaN / NOT NaN
pred := iceberg.UnaryPredicate(iceberg.OpIsNull, iceberg.Reference("col"))

// Literal predicates: <, <=, >, >=, ==, !=, STARTS WITH, NOT STARTS WITH
lit := iceberg.NewLiteral(int64(42))
pred := iceberg.LiteralPredicate(iceberg.OpEQ, iceberg.Reference("col"), lit)

// Set predicates: IN / NOT IN
lits := []iceberg.Literal{iceberg.NewLiteral("a"), iceberg.NewLiteral("b")}
pred := iceberg.SetPredicate(iceberg.OpIn, iceberg.Reference("col"), lits)

Concurrent Writes

When multiple writers commit to the same table, iceberg-go uses optimistic concurrency control: every commit is validated against the table state it was built on. If another writer committed first, the commit is rejected rather than silently clobbering their snapshot.

Conflict detection

Each producer (Append, Overwrite, Delete, RowDelta, RewriteDataFiles) runs a set of validators before the commit lands. They check that the files the operation assumed (added, deleted, or filtered) still match the current table state. A failed validation surfaces as one of:

  • table.ErrCommitFailed — the base snapshot moved on; the commit can be retried after refreshing (see below).
  • table.ErrCommitDiverged — terminal. The base snapshot is no longer on the branch at all, so a retry cannot reconcile the change.
  • table.ErrDataFilesMissing — terminal. Data files that the operation references, such as the target of a position delete or deletion vector, are not live, so retrying the same delete cannot succeed. Rebuild the delete against the current table. When Transaction.Commit returns it, the error also matches ErrTransactionUnusable.
  • table.ErrDuplicateDataFiles — terminal for the requested paths. A RowDelta rejects repeated paths during staging and checks whether a concurrent commit added any of its paths that are still live on retry. AddDataFiles and AddDataFilesByPath make the same retry check unless the duplicate check is disabled (WithoutDuplicateCheck or ignoreDuplicates). A retry collision also matches ErrTransactionUnusable. Use distinct paths in a new operation.
  • table.ErrTransactionUnusable — this transaction can't be committed again. If the error also matches ErrCommitFailed, retry in a new transaction from a reloaded table.
import (
    "context"
    "errors"

    "github.com/apache/iceberg-go/table"
)

_, err := txn.Commit(context.Background())
switch {
case errors.Is(err, table.ErrDuplicateDataFiles):
    // choose different data file paths before building a new RowDelta
case errors.Is(err, table.ErrTransactionUnusable) && errors.Is(err, table.ErrCommitFailed):
    // a concurrent change: retry in a new transaction from a reloaded table
case errors.Is(err, table.ErrCommitDiverged), errors.Is(err, table.ErrTransactionUnusable):
    // unrecoverable: rebuild the operation from the latest table
case errors.Is(err, table.ErrCommitFailed):
    // retriable: refresh and try again (the retry loop does this for you)
case errors.Is(err, table.ErrCommitRejected):
    // the catalog wrote nothing: fix the cause, then call Commit again
}

A commit can also fail with table.ErrCommitRejected, which means the catalog rejected it before writing anything, for example an update the catalog can't apply or a REST 400, 401, 403 or 404. The commit is not retried, and the transaction can still be committed.

Isolation levels

Delete and update operations are validated under an isolation level, set per operation through table properties:

PropertyDefaultValues
write.delete.isolation-levelserializableserializable, snapshot
write.update.isolation-levelserializableserializable, snapshot

serializable rejects the commit if any concurrent snapshot added data matching the operation's filter. snapshot is more permissive — it only rejects when concurrent deletes touch the same files.

Automatic retry

On each retry, iceberg-go reloads the table metadata, applies staged changes in order and runs the producer's validators against the fresh snapshot. It submits the commit only if it is still valid. An append staged after a rollback is rebuilt on the rollback target.

RollbackToSnapshot, AssertRefSnapshotID, and CherryPickSnapshot pin the refs they guard. If a pinned ref moves, the commit fails instead of rewriting that assertion to the new head. Cherry-picks can retry table-level conflicts when their pinned refs stay unchanged. A divergent replay onto a new branch also pins main; a fast-forward onto a missing branch points directly to the source snapshot and does not depend on main.

Each replayed snapshot from a staged write gets the current timestamp, or one millisecond after its parent if that is later. Its timestamp reflects the attempt that commits it, not staging time.

RollbackToSnapshot, AssertRefSnapshotID, FastForwardBranch, ReplaceBranchFromRef, and ReplaceBranch pin the refs they guard. Promoting from a ref pins both the source and target. If the source points to a snapshot staged in the same transaction, promotion also pins the commit branch, preventing retry from rebuilding that source on a different history. If a pinned ref moves, the commit fails instead of rebasing a co-staged append. ExpireSnapshots does not pin refs. Retries replan it as described in Snapshot expiration.

Commit retries a conflict up to 4 times by default (commit.retry.num-retries is 4, as in Java and PyIceberg). Set it to 0 to fail on the first conflict; see Manifest and commit in the configuration reference for the other retry properties:

// Fail on the first conflict instead of retrying.
_, err := cat.CreateTable(ctx, ident, schema,
    catalog.WithProperties(iceberg.Properties{
        "commit.retry.num-retries": "0",
    }),
)

Catalog support: the REST, SQL, Glue, Hive, and Hadoop catalogs report commit conflicts, including requirements that fail because of a concurrent change, as ErrCommitFailed, so the retry loop engages on all of them. A commit on another branch that takes the staged snapshot's sequence number or first-row-id is a conflict too, and the retry renumbers the snapshot.

Snapshot-ID assertions cannot detect concurrent retention-only edits. REST catalogs also cannot detect a ref type change that leaves its snapshot ID unchanged. Avoid editing ref retention concurrently with branch promotion.

Only the implicit assertion on the commit branch's head is rebased after a refresh. Other requirements, including the schema, spec, sort order, and pinned refs, must still hold. Otherwise, the commit fails without another attempt and the transaction is unusable.

After a conflict, calling Commit again refreshes the table and replays staged changes even with retries disabled. Each call gets the configured retry budget. A commit that removes delete files and cannot be replayed resubmits only if its branch has not moved.

A staged change that cannot apply to the refreshed table makes the transaction unusable. For example, a staged format upgrade cannot apply if a peer has already committed a higher format version. The error keeps its cause, so it also matches ErrCommitFailed when the cause is a conflict. See ErrTransactionUnusable for all conditions that end the transaction after refresh.

A failed commit keeps the files it staged until a later commit lands. A transaction you abandon leaves them for orphan file removal, as one with retries disabled always has. An abandoned manifest rewrite also leaves the manifests that later attempts merged. TableCommit refuses a transaction whose commit failed, since the multi-table path does not refresh. Call Commit to resume it, or build a new transaction.

Snapshot expiration

A retry replays staged changes in order against the refreshed table. It replans each ExpireSnapshots call at its original position, with the original options and cutoff time. The plan retains snapshots that a concurrent commit made reachable, such as rollback targets and new branch heads. It can expire snapshots that a concurrent append moved outside the retention window. A transaction that appends and expires snapshots rebases onto a concurrent append like any other append.

Each attempt requires the refs read by expiries that remove snapshots or refs to be unchanged since loading or refreshing the table. An expiry that removes nothing adds no such requirement. If a concurrent commit moves one of those refs before the attempt succeeds, it causes another conflict. The next attempt replans the expiry. If a concurrent commit creates a ref that the plan did not read, that ref does not cause a conflict. Expiring its snapshot also removes the ref.

  • Retries replan an expiry even if staging or an earlier attempt produced no expiry updates.
  • A retry stamps snapshots staged earlier in the transaction after the expiry's cutoff, so the retry keeps them even if the staged plan expired them.
  • If no updates remain, for example because a concurrent commit already expired the same snapshots, Commit returns the refreshed table without committing.
  • A transaction containing only expiries with no updates makes no commit attempt and never refreshes or replans.
  • Post-commit cleanup deletes files for snapshots expired by the successful attempt, if cleanup is enabled.

A retry fails with ErrTransactionUnusable if GC is disabled after refresh, a staged change no longer applies, or replanning changes whether a non-main commit branch is removed. ErrTransactionUnusable and ErrCommitFailed list these cases and which of them a new transaction can retry.

Metrics Reporting

Iceberg Go implements Iceberg's Metrics Reporting API. After scan planning it can emit a ScanReport (files and manifests considered, scanned, and skipped; bytes read; planning duration), and after a commit a CommitReport (commit attempts, duration, and the added/removed/total file, record, and delete counts). These metrics are otherwise invisible from outside the client; a reporter gives operators a standard way to collect them.

A pluggable metrics.Reporter is the sink that receives those reports.

The skipped-data-files and skipped-delete-files counters track file entries rejected by partition or metrics filters in manifests the planner reads. The skipped-manifest counters track pruning at the earlier manifest level.

Opt-in by default

Reporting is strictly opt-in. With no reporter configured the instrumented code paths do no work, and the client emits no logs and no network traffic.

This is a deliberate divergence from Iceberg Java, which defaults to the logging reporter. A library must not start emitting output the caller never asked for, so Iceberg Go defaults to a no-op reporter until you select one. Callers migrating from Java that want reports by default must select the logging reporter explicitly.

Selecting a reporter

Catalog-wide, via a property

Set metrics-reporter-impl to a registered reporter name. Every table loaded from the catalog inherits it. This works for REST-catalog config too, since it is an ordinary catalog property.

cat, err := catalog.Load(ctx, "prod", iceberg.Properties{
    "metrics-reporter-impl": "logging", // built-in: "nop" (default) or "logging"
})

An unrecognized name is an error, so a typo surfaces rather than silently disabling metrics.

Per-scan override

Override the reporter for a single scan with table.WithReporter; it takes precedence over the reporter inherited from the table.

inmem := &metrics.InMemoryReporter{}

scan := tbl.Scan(table.WithReporter(inmem))
// ... run the scan ...

for _, report := range inmem.Reports() {
    if sr, ok := report.(metrics.ScanReport); ok {
        fmt.Println(sr.TableName, sr.Metrics.ResultDataFiles)
    }
}

Built-in reporters

ReporterPurpose
metrics.NopReporter{}Discards every report. The default when nothing is configured.
metrics.NewLoggingReporter(logger)Logs each report via an slog.Logger (slog.Default() when nil). Registered as "logging".
&metrics.InMemoryReporter{}Retains every report for inspection via Reports(); Reset() clears them. Intended for tests.
metrics.Combine(reporters...)Fans each report out to several reporters. A panic in one is isolated from the rest.

Writing a custom reporter

Implement the two-method Reporter interface and type-switch on the concrete report:

type myReporter struct{}

func (myReporter) Report(ctx context.Context, report metrics.MetricsReport) {
    switch r := report.(type) {
    case metrics.ScanReport:
        // record r.Metrics ...
    case metrics.CommitReport:
        // record r.Metrics ...
    }
}

func (myReporter) Close() error { return nil } // release any held resources

Two contract rules matter:

  • Never block or fail the operation. Report is called inline at the scan/commit completion point. A network-backed reporter must dispatch the send on a background worker, and any error must be handled internally (logged and swallowed), never returned to the caller.
  • Be safe for concurrent use. Report may be called from multiple goroutines.

To make a custom reporter selectable by name from metrics-reporter-impl, register a factory for it (typically from init):

func init() {
    metrics.Register("my-reporter", func(props map[string]string) (metrics.Reporter, error) {
        return myReporter{}, nil
    })
}

Reporting to a REST catalog

A REST catalog can also POST each report to the catalog's .../tables/{table}/metrics endpoint. This is a separate opt-in from the in-process reporter above and is off by default; the POST is dispatched on a background worker so it never stalls a scan or commit. See the REST metrics-reporting properties for the enablement flag and timeout.

OpenTelemetry

Experimental. The OpenTelemetry metric and attribute names track the still-unmerged Iceberg Java reporter (apache/iceberg#16250) and may change to stay aligned with it.

The metrics/otel package provides an OpenTelemetry-backed reporter. The host owns the OpenTelemetry SDK; the reporter only looks up a meter (the global MeterProvider by default, or one you pass with WithMeter).

import "github.com/apache/iceberg-go/metrics/otel"

rep, err := otel.NewReporter(
    otel.WithMeter(meter),
    otel.WithAttributes(otel.AttrTableName, otel.AttrOperation),
)

It exports a curated subset of the report fields under iceberg.scan.* / iceberg.commit.* instrument names (e.g. iceberg.scan.planning.duration, iceberg.scan.result.data_files, iceberg.commit.duration, iceberg.commit.data_files.added).

Instrument types follow the meaning of each field. Durations are histograms (in milliseconds). The commit *.total fields (iceberg.commit.records.total, iceberg.commit.data_files.total, iceberg.commit.delete_files.total, iceberg.commit.file_size.total_bytes, iceberg.commit.positional_deletes.total and iceberg.commit.equality_deletes.total) describe the table after the commit, so they are gauges that hold the last reported value; do not sum them over time. Everything else (added/removed deltas, attempts, manifest stats and all scan fields) is a monotonic counter. Gauges are last-write-wins per attribute set, so dropping the table name from WithAttributes makes different tables overwrite each other's totals.

WithAttributes bounds label cardinality by allowlist. The default set is table name + operation; schema id (otel.AttrSchemaID) is opt-in. The snapshot id is never attached as a metric attribute because it is unbounded — per-snapshot detail stays available through the full reports and the table's snapshot history.

The OpenTelemetry reporter is not registered under a metrics-reporter-impl name automatically. To select it by property, register a factory for it as shown in Writing a custom reporter; otherwise pass the instance to table.WithReporter or table.WithMetricsReporter.

Picking Up Issues

Before starting work on an issue:

  1. Check for existing PRs. Search the open pull requests to make sure nobody is already working on it.
  2. Claim the issue. Leave a comment on the issue (e.g., "I'd like to work on this") and wait for a maintainer to acknowledge before writing code.
  3. One at a time for new contributors. If you haven't had a PR merged into iceberg-go yet, please work on one issue at a time. Get it reviewed, address feedback, get it merged — then pick up the next one. This helps us give your work the attention it deserves and avoids wasted effort from overlapping contributions.

If two PRs land for the same issue, we will generally keep the one from the contributor who claimed it first.

Submitting a Pull Request

  • Reference the issue number in your PR description (e.g., "Fixes #123").
  • Keep PRs focused — one issue per PR.
  • Run make test and make lint before pushing. CI runs all of these too, but catching issues locally saves a round-trip. make lint-install will install the linter if you don't have it yet.
  • All commits must have a Signed-off-by line (DCO).
  • CI checks the exported API against the base branch with apidiff. If your PR changes it incompatibly on purpose, mark the PR title as breaking with a !, for example refactor(io)!: add context to IO.Open. You can run the same check locally with dev/check-api-compat.sh after installing the apidiff version it names.

Code Review

  • Maintainers may request changes. This is normal — it doesn't mean the PR is bad, it means we want to get it right.
  • Respond to review comments by pushing new commits (don't force-push over reviewed code).
  • If your PR has been waiting for review for more than a few days, ping on Slack.

Unreleased compatibility notes

  • AddDataFiles and AddDataFilesByPath no longer add a file twice on retry. When a commit retry finds that a concurrent commit already added one of the same paths, the commit now fails with table.ErrDuplicateDataFiles, which also matches table.ErrTransactionUnusable. Previously, the retry added the file a second time and scans returned its rows twice. With WithoutDuplicateCheck or ignoreDuplicates=true, the retry still adds the file again, as before.

  • gocloud types are no longer exposed by blobfs and gcs. blobfs.New now returns the blobfs.FileIO interface, which lists the iceberg-go io interfaces and io.Closer, instead of a struct that embeds *blob.Bucket. FileIO.NewWriter, blobfs.Writer and gcs.ParseGCSConfig are removed; use Create, or configure GCS through properties. To migrate, replace *blobfs.FileIO with blobfs.FileIO in fields, signatures and var _ X = (*blobfs.FileIO)(nil) assertions, and assert Sys() results to blobfs.FileIO instead of *blobfs.FileIO.

  • Catalog and view FileIO may use isolated registries. Glue, Hadoop, Hive and SQL accept WithIORegistry, as REST already does. hadoop.NewCatalog, sql.NewCatalog, view.CreateView, view.CreateViewWithIOProperties, view.CreateViewFromVersion and view.WriteMetadata now take a trailing variadic option. Existing calls still compile. Function values assigned to a type with the old signature need a wrapper that calls the function without options. The default remains the global registry, including for catalog.Load.

  • RowDelta.Commit can be called once per builder. A second Commit on the same RowDelta now returns an error wrapping table.ErrInvalidOperation and stages nothing, even if the first call failed, as RewriteFiles.Commit does. Previously, calling Commit again after a failed first call could succeed, and calling it again after a successful one staged the builder's files a second time. Create a new builder with Transaction.NewRowDelta for each commit.

  • Data-file replacements now reject concurrent deletes. Commits staged through ReplaceDataFiles, ReplaceDataFilesByPath, ReplaceFiles, or rewrite operations can return table.ErrConflictingDeleteFiles when a concurrent position delete targets a replaced file or any concurrent equality delete is added. Compaction on tables with streaming equality deletes may see additional conflicts.

  • Orphan cleanup now rejects gc.enabled=false. DeleteOrphanFiles, PlanOrphanFiles, ExecuteOrphanCleanup, and dry runs now return an error before filesystem access. The iceberg clean-orphan-files command is also affected.

  • Orphan cleanup requires complete snapshot history. DeleteOrphanFiles, PlanOrphanFiles, ExecuteOrphanCleanup, dry runs, and iceberg clean-orphan-files now reject tables loaded with REST snapshot-loading-mode=refs, returning an error wrapping table.ErrInvalidOperation. Configure the REST catalog with snapshot-loading-mode=all (or omit it) and reload the table; a server override that forces refs prevents cleanup through that catalog. maintenance.PurgeFiles is unaffected.

  • Partition specs reject source types a transform cannot handle. Creating or updating a spec with an incompatible source, such as day(string), now fails. Writes to existing incompatible specs return ErrInvalidTransform instead of writing null partition values.

  • REST CreateTable validates the partition spec locally. Invalid specs, including transforms with incompatible source types, return an error matching iceberg.ErrInvalidPartitionSpec before the create request. Previously, the server could return rest.ErrBadRequest.

  • New partition specs reject multiple sources for built-in transforms. Create-table and add-spec payloads with this shape return ErrInvalidPartitionSpec. Historical metadata with such a field still loads and round-trips, but the field is skipped during partition pruning and residual simplification. Multi-source unknown transforms remain supported.

  • Unsigned partition values no longer wrap. Partitioned writes accept the full Arrow uint32 range for Iceberg long sources and return iceberg.ErrInvalidArgument when an unsigned value exceeds the destination’s signed range.

  • Invalid name mappings now stop scans and add-files. Tables with an unparseable schema.name-mapping.default now return ErrInvalidMetadata on scans and add-files instead of ignoring the mapping. Fix the property with a valid mapping or remove it.

  • SigV4 keeps the token or credential as Original-Authorization. With rest.sigv4-enabled=true (or rest.auth.type=sigv4) and a token or credential, requests used to be signed with the token silently dropped, because the SigV4 signature replaced the Authorization header. They now carry it as Original-Authorization, included in the signed headers, as Iceberg Java does. A server behind SigV4 that ignores the header is unaffected.

  • Float and double literal comparators use Iceberg ordering. TypedLiteral.Comparator() now orders -0.0 before +0.0 and NaN after all other values; NaN compares equal to NaN. Callers that use these public comparators may see a different order or equality result.

  • Table creation rejects duplicate field IDs. NewMetadata, and CreateTable on catalogs that build metadata through it (not REST), now return ErrInvalidSchema when two fields in the schema share an ID, including unset 0 or -1 IDs, even for unpartitioned, unsorted tables. Before, the partition spec or sort order could bind to the wrong column. Callers should assign unique IDs (or let the schema be built with fresh IDs). This matches Java, whose Schema constructor rejects duplicate IDs.

  • Struct defaults must be empty objects. Non-null initial-default and write-default values for struct fields must be {}; defaults for nested fields belong on those fields. Tables with populated struct defaults written by older iceberg-go versions still load, but AddSchema validates the entire resulting schema. Any schema update, including one that changes an unrelated column, will fail until the populated default is cleared.

  • Schemas with duplicate field IDs are rejected. Table and view metadata now fail to load with ErrInvalidSchema if any schema in their history has two fields sharing an ID, including 0 or -1; Java Iceberg already rejects these. Older releases could write such schemas through SQL CreateView, view.CreateView or view.NewMetadata, or through CommitTable with NewAddSchemaUpdate on non-REST catalogs, when IDs were left unset; these calls, and the new UpdateView, now return ErrInvalidSchema instead. To recover, drop and recreate an affected view. For a table, point the catalog at a copy of the metadata without that schema through an atomic catalog metadata replacement, instead of editing the currently referenced metadata file in place.

  • Sort order replacements reuse orders staged earlier in the same transaction. If a transaction replaces order A with B and then returns to A, A becomes the default again instead of B. The final update reuses A's ID instead of adding another definition. Reuse of orders from earlier commits was already supported.

  • Case-insensitive field binding rejects only ambiguous names. Reference.Bind and Schema.Select return ErrInvalidSchema when the requested case-insensitive name matches different field IDs, and the error includes both names. Unrelated names remain available to scans, writes, and schema, partition, and sort order updates.

  • Delete files now have a separate 64 MiB target. Equality-delete and v2 position-delete files previously used write.target-file-size-bytes (512 MiB by default, or the table's override) as their file-size target. They now use write.delete.target-file-size-bytes, which defaults to 64 MiB. After upgrading, tables may produce more, smaller delete files unless this new property is set. To preserve the previous delete-file size target, set write.delete.target-file-size-bytes to the table's former effective write.target-file-size-bytes value (536870912 when the data-file target was unset). The data-file target itself is unchanged.

  • Schema updates reject read-time type casts. UpdateSchema.UpdateColumn now allows only Iceberg schema promotions. Changes such as string to binary and fixed[16] to uuid are rejected by default.

  • Schema reads now reject invalid identifier fields. Table and view metadata with identifier-field-ids referring to an optional, float/double, missing, non-primitive, or improperly nested field now fails to load with invalid schema (for example, invalid schema: identifier field "foo" must be required or invalid schema: identifier field "foo" cannot be float or double). Older iceberg-go releases could load such metadata, but Java Iceberg already rejects it. To recover an affected table, back up its metadata and use an atomic catalog metadata repair to remove the invalid identifier IDs or replace them with IDs of existing, required, non-floating primitive fields nested only in required structs. Do not edit the currently referenced metadata file in place. Repeated identifier IDs are deduplicated on read.

  • Table history logs reject missing or null required fields. Loading table metadata now fails with table.ErrInvalidMetadata if a snapshot-log entry omits or sets snapshot-id or timestamp-ms to null, or a metadata-log entry omits or sets metadata-file or timestamp-ms to null. Older iceberg-go releases silently accepted omitted or null fields as zero values, but Java Iceberg already rejects such metadata. Explicit zero values remain valid. Repair affected metadata through an atomic catalog metadata replacement instead of editing the currently referenced metadata file in place.

  • UpdateSchema rejects deleting an identifier field. DeleteColumn on an identifier column used to succeed and quietly drop the column from the table's identifier fields. Now Apply (and Commit) fails with cannot delete identifier field …, as in Java. Deleting a struct that contains one already failed, and now reports cannot delete field … as it will delete nested identifier field …. To delete the column anyway, also call SetIdentifierField with the identifier fields the schema should keep (for example SetIdentifierField([][]string{}) to clear them). This also stops a new column that reuses a deleted identifier column's name from becoming the identifier.

  • Schema updates rewrite the table's name mapping. When a table has schema.name-mapping.default, every UpdateSchema commit now updates it, as in Java and PyIceberg; before, it changed only when WithNameMapping was passed. Added columns are mapped by name and renamed columns keep their old names, so data files without field IDs resolve them. If a new column reuses a name freed by DeleteColumn or RenameColumn, that name now maps to the new column: in older files without field IDs, the new column reads the values stored under that name, and a renamed column no longer reads them. Tables without the property are unaffected.

  • Schema JSON defaults preserve integer precision. long defaults now decode as int64 instead of float64; non-integral, non-numeric, or out-of-range values now fail to parse. Numeric literals inside object and list defaults decode as json.Number rather than float64.

  • REST mutation keys can enable transport replay. Namespace, table, view, transaction and scan-cancellation mutations listed in the REST catalog documentation now carry fresh UUIDv7 Idempotency-Key headers when GET /v1/config returns a non-null idempotency-key-lifetime. Go's HTTP transport may replay certain failed requests on reused connections with the same key; the advertised lifetime is not yet enforced. Scan plan and task key handling is unchanged. When a lifetime is advertised, a default Idempotency-Key configured via WithHeaders is dropped after GET /v1/config.

NumFields() and Field(i) read fields without copying, and NewListType and NewMapType are the constructors for the other nested types. The struct's field list is no longer exported; see the next note.

  • Nested type fields are unexported. StructType, ListType and MapType can no longer be built with keyed struct literals, and their fields can no longer be assigned (see #2062). Build them with NewStructType, NewListType and NewMapType, and to change one, build a new value. Read them through methods named after the old fields:

    • StructType.FieldList becomes Fields() (a copy), or NumFields() and Field(i) to read without copying.
    • ListType.ElementID, Element and ElementRequired become ElementID(), Element() and ElementRequired().
    • MapType.KeyID, KeyType, ValueID, ValueType and ValueRequired become KeyID(), KeyType(), ValueID(), ValueType() and ValueRequired().
    • Schema.IdentifierFieldIDs is unexported too and becomes IdentifierFieldIDs(), which returns a copy. Set the IDs with NewSchemaWithIdentifiers, which keeps its own copy of the slice it is given.

    Pointers to these types and Schema encode to the same JSON as before. Values of these types, such as the result of Schema.AsStruct(), now encode like pointers instead of a partial form without "type", in which list and map values also dropped their element, key and value types.

  • io.StatIO.Stat accepts a context. The method now takes a context.Context before the path, so custom StatIO implementations and callers must pass the operation context.

  • Commits retry conflicts by default. commit.retry.num-retries now defaults to 4, as in Java and PyIceberg, so Commit refreshes and replays a conflicting commit up to four times before returning ErrCommitFailed. Set it to 0 to keep failing on the first conflict. table.CommitNumRetriesDefault changes from 0 to 4.

  • The first Delete on a v3 table upgraded from v2 can fail with ErrCommitFailed. A merge-on-read Delete that gives a data file its first deletion vector now folds that file's v2 position deletes into the vector, so those deletes no longer reappear after the upgrade, and drops the file-scoped v2 position delete files in the same commit. Like any commit that removes delete files, it is not replayed: if another writer commits first, it returns ErrCommitFailed instead of refreshing and retrying. Reload the table and run the delete again. Partition-scoped position delete files stay in the table.

  • Schema updates assert the last assigned field ID. When UpdateSchema adds a schema, the commit now also requires the table's last-column-id to match the transaction's base, as Iceberg Java does. A stale writer whose base predates another writer's column additions now fails with table.ErrCommitFailed instead of reusing field IDs. Reload the table and reapply the schema change.

  • Schemas store binary and fixed defaults as hex strings. NewSchema, NewSchemaWithIdentifiers and UpdateSchema.AddColumn (through Apply()) convert []byte, BinaryLiteral and FixedLiteral defaults of binary and fixed fields, including fields nested in structs, lists and maps, to the lowercase hex string iceberg-go writes to metadata JSON, so a field read back from a schema holds a string such as "0aff". Code that type-asserts these defaults to []byte must decode the string instead, for example with hex.DecodeString. A schema built in process now equals the same schema read from metadata with lowercase hex. Equals compares the strings case-sensitively, and Java writes uppercase hex (see apache/iceberg#18352). The fields and types passed in are not modified.

  • Predicates reject NaN literals when bound. EqualTo, NotEqualTo, LessThan, LessThanEqual, GreaterThan, GreaterThanEqual, IsIn, NotIn and LiteralPredicate/SetPredicate with a NaN float literal now fail in Bind with ErrInvalidArgument, as Java does. That includes the string "NaN" on a float column and a NaN on a decimal column, which used to bind as zero. Scans, ExpressionEvaluator and the metrics evaluators all bind first, so they return the error too. Use IsNaN and NotNaN to match NaN values.

Scans and ExpressionEvaluator return the error for these filters instead of comparing a wrapped value.

  • Name mapping rejects ambiguous aliases and duplicate field IDs. Scans of files without field IDs now return ErrInvalidSchema when the same name belongs to multiple mapped fields at one level, instead of silently choosing the first.     Relatedly, the previously unexported isGCEnabled is now table.IsGCEnabled, so the new package can gate destructive operations on the gc.enabled table property.

  • Metadata tables moved to table/inspect. Table.Inspect and InspectTable are removed. Each metadata table is now a free function in the table/inspect package that takes the table as its second argument, matching table/maintenance. For example, tbl.Inspect().Snapshots(ctx) becomes inspect.Snapshots(ctx, tbl). As with table/maintenance, table/inspect imports table, so table.Table cannot keep a deprecation shim. The following moved from table to table/inspect:

    • Functions (now free functions taking the context, *table.Table and options): History, Snapshots, Manifests, Refs, MetadataLogEntries, Entries, AllEntries, Files, DataFiles, DeleteFiles, AllFiles, AllDataFiles, AllDeleteFiles, AllManifests, Partitions, PositionDeletes.
    • Schema constructors: HistorySchema, SnapshotsSchema, ManifestsSchema, RefsSchema, MetadataLogEntriesSchema, EntriesSchema, AllEntriesSchema, FilesSchema, DataFilesSchema, DeleteFilesSchema, AllFilesSchema, AllDataFilesSchema, AllDeleteFilesSchema, AllManifestsSchema, PartitionsSchema, PositionDeletesSchema.
    • Options: InspectOption is now inspect.Option, and WithInspectAllocator is now inspect.WithAllocator.

    DiffSnapshotFiles and ValidateSnapshot stay in table as Table methods: tbl.Inspect().DiffSnapshotFiles(ctx, from, to) becomes tbl.DiffSnapshotFiles(ctx, from, to), and tbl.Inspect().ValidateSnapshot(ctx, id) becomes tbl.ValidateSnapshot(ctx, id). ManifestProvider.UniqueManifests is newly exported for the all_* tables.

  • Data-file replacement methods renamed. Use ReplaceDataFilesByPath for string paths. Use ReplaceDataFiles for prebuilt DataFile values instead of ReplaceDataFilesWithDataFiles.

  • maintenance.PurgeFiles (previously Table.PurgeFiles) now calls IO.Remove concurrently, with up to 32 calls in flight, when the filesystem does not implement BulkRemovableIO. Custom IO implementations, including those registered with io.Register, must make Remove safe for concurrent use and synchronize any shared mutable state. The bulk deletion path is unchanged.

  • Snapshot summaries report deletion vectors separately. On v3 tables, DVs are counted under added-dvs and removed-dvs instead of added-position-delete-files and removed-position-delete-files. added-files-size and removed-files-size use each DV's content_size_in_bytes instead of its whole Puffin file, so they go down for commits with DVs. total-files-size is updated from these values. Partition summaries, commit reports and OTel metrics change the same way. Existing snapshots are not rewritten.

  • Deletion vectors identify row positions. New Puffin blobs list _pos field ID 2147483645 in fields, matching Iceberg Java. Existing files are unchanged.

  • Partition and sort source accessors renamed. Replace PartitionField.SourceID() and SortField.SourceID() with FirstSourceID(). Their behavior and serialized fields are unchanged.

  • Row-lineage column predicate renamed. Use iceberg.IsRowLineageColumn instead of iceberg.IsMetadataColumn to identify _row_id and _last_updated_sequence_number. Use iceberg.IsReservedFieldID to check the full reserved metadata field ID range.

  • File writes and directory walks now take an operation context. Update WriteFileIO and ListableIO implementations and calls to Create, WriteFile, and WalkDir to pass context.Context; cloud writes and listings use it for cancellation.

  • In and NotIn follow SQL semantics for NULL. A multi-valued NotIn, NOT(In(...)) and NOT(NotIn(...)) no longer match rows where the column is NULL, consistent with NotEqual. A predicate under NOT on a column missing from an older data file no longer matches every row of that file; those rows match as a stored NULL would. Java's Evaluator still matches NULL for notEq and notIn, see apache/iceberg#18701.

  • Commit rejections now match table.ErrCommitRejected. SQL, Glue, Hive and Hadoop failures while preparing metadata, plus REST commit responses 400, 401, 403 and 404, leave transactions committable (after a REST 404, the next Commit fails when it reloads the table). Existing errors.Is matches keep working, but SQL, Glue, Hive and Hadoop rejection messages now start with commit rejected: , so code that matches error text may need updating.

  • Float comparisons against literals beyond the float32 range follow IEEE 754. On a float32 column, x < 1e100 no longer returns NaN, +Inf or NULL rows, and NOT(x > 1e100) no longer returns NULL rows. An infinite literal now binds to a float32 infinity, so x = +Inf matches +Inf rows. Java still folds these comparisons to always true or false, see apache/iceberg#18700.

  • Orphan cleanup refreshes metadata before deletion. Non-dry-run DeleteOrphanFiles requires a catalog-backed table and refreshes it before planning and again before deleting files. ExecuteOrphanCleanup also refreshes before deleting from a non-empty plan. If a saved plan is stale, refresh or reload the table before planning again. Dry runs still work without a catalog.

  • Position deletes use the data file's partition spec. After partition spec evolution, Delete on a merge-on-read table wrote v2 position delete files with the current spec instead of the target data file's spec. Scans and re-running Delete on such a table can fail with invalid metadata: position delete file ... uses partition spec N, but data file ... uses partition spec M; some deletes are instead silently missed, so the rows stay visible, and re-running those deletes applies them. New deletes carry the data file's spec. For the mismatch error, remove the delete files whose spec ID differs from their data file's with Transaction.NewRewrite (RewriteFiles.DeleteFile), then re-run those deletes; until then the rows they deleted are visible again.

Verifying and producing releases

If you are validating an RC or cutting a new release, see:

  • Verify a release - what to do when a [VOTE] thread is posted on dev@iceberg.apache.org.
  • How to release - PMC/committer process for cutting an RC and publishing.

Verify a release

When a release candidate is announced on dev@iceberg.apache.org, anyone (committer or not) can help by verifying the artifacts. Verification is required from at least three Apache Iceberg PMC members for the vote to pass.

The repository ships a script that performs the full verification end-to-end: dev/release/verify_rc.sh.

What an RC announcement contains

A [VOTE] iceberg-go X.Y.Z RC<N> thread on dev@iceberg.apache.org will reference:

  • A signed source tarball under https://dist.apache.org/repos/dist/dev/iceberg/apache-iceberg-go-${VERSION}-rc${RC}/ (.tar.gz, .tar.gz.asc, .tar.gz.sha512)
  • The Apache Iceberg KEYS file at https://downloads.apache.org/iceberg/KEYS
  • A GitHub compare URL between the previous release tag and the new RC tag

Prerequisites

The script requires:

  • curl
  • gpg
  • shasum or sha512sum
  • tar
  • Java and Python 3 for the RAT license check
  • jq if the script needs to download Go

Use a Go toolchain that meets the requirement in the candidate's go.mod. If Go is unavailable, the script downloads a toolchain for verification.

Import the Apache Iceberg KEYS

curl https://downloads.apache.org/iceberg/KEYS -o KEYS
gpg --import KEYS

Run the verification script

Pass the version and RC number. Use a disposable module cache because the script cleans it on exit. Run with GITHUB_TOKEN unset to keep it out of shell traces if the script downloads Go.

env -u GITHUB_TOKEN GOMODCACHE="$(mktemp -d)" dev/release/verify_rc.sh ${VERSION} ${RC}

For example, to verify 0.6.0 RC1:

env -u GITHUB_TOKEN GOMODCACHE="$(mktemp -d)" dev/release/verify_rc.sh 0.6.0 1

If the verification succeeds, the script prints:

RC looks good!

Optional environment variables

verify_rc.sh honors these environment variables (all optional):

VariableDefaultEffect
VERIFY_DEFAULT1Master switch propagated to VERIFY_DOWNLOAD and VERIFY_SIGN if they are unset.
VERIFY_DOWNLOAD${VERIFY_DEFAULT}Re-download artifacts when 1; reuse the local copy when 0.
VERIFY_SIGN${VERIFY_DEFAULT}Verify the signature when 1. The script always checks the checksum.
VERIFY_FORCE_USE_GO_BINARY0When 1, ignore any system Go and use the script's auto-downloaded Go.

Manual verification fallback

If you would rather verify by hand, the underlying steps are:

# Download the artifacts
curl -O https://dist.apache.org/repos/dist/dev/iceberg/apache-iceberg-go-${VERSION}-rc${RC}/apache-iceberg-go-${VERSION}.tar.gz
curl -O https://dist.apache.org/repos/dist/dev/iceberg/apache-iceberg-go-${VERSION}-rc${RC}/apache-iceberg-go-${VERSION}.tar.gz.asc
curl -O https://dist.apache.org/repos/dist/dev/iceberg/apache-iceberg-go-${VERSION}-rc${RC}/apache-iceberg-go-${VERSION}.tar.gz.sha512

# Verify the signature
gpg --verify apache-iceberg-go-${VERSION}.tar.gz.asc apache-iceberg-go-${VERSION}.tar.gz

# Verify the checksum (or sha512sum -c on systems without shasum)
shasum -a 512 --check apache-iceberg-go-${VERSION}.tar.gz.sha512

# Inspect the archive, check licenses, and run the unit tests
archive="apache-iceberg-go-${VERSION}"
tar xf "${archive}.tar.gz"
(
  cd "${archive}"
  dev/release/run_rat.sh "../${archive}.tar.gz"
  go test ./...
)

You should reply to the [VOTE] thread with +1, +0, or -1 and a one-line description of what you verified (for example, "verified signatures, checksums, and verify_rc.sh passed on macOS arm64").

How to release

This page is for Apache Iceberg PMC members and committers who are cutting a new Apache Iceberg Go release. The canonical scripts live in dev/release/ and dev/release/README.md is the source of truth - this page mirrors it and adds context.

Requirements

  • You must be an Apache Iceberg committer or PMC member.

  • Install GitHub CLI, Subversion, and sha512sum for candidate preparation. Publishing also uses sort --version-sort.

  • You must prepare a PGP key for signing. See https://infra.apache.org/release-signing.html#generate.

  • Your PGP key must be registered in the Apache Iceberg KEYS file at https://downloads.apache.org/iceberg/KEYS. To add a key:

    svn co https://dist.apache.org/repos/dist/release/iceberg
cd iceberg
$EDITOR KEYS
svn ci KEYS

  • You must run the release scripts from a working copy whose origin remote is git@github.com:apache/iceberg-go.git (not your fork). release_rc.sh enforces this.

Overview

  1. Test the revision to be released.
  2. Prepare an RC and start a vote.
  3. On a passing vote, publish.

Prepare an RC and vote

Run dev/release/release_rc.sh against the canonical clone:

git clone git@github.com:apache/iceberg-go.git
cd iceberg-go
GH_TOKEN=${YOUR_GITHUB_TOKEN} dev/release/release_rc.sh ${VERSION} ${RC}

Example for 0.6.0 RC1:

GH_TOKEN=${YOUR_GITHUB_TOKEN} dev/release/release_rc.sh 0.6.0 1

The arguments are the version and the RC number. If RC1 has a problem, increment the RC number to RC2, RC3, and so on.

release_rc.sh will:

  • Tag vX.Y.Z-rc<N> and push the tag.
  • Create a signed source tarball.
  • Upload the artifacts to https://dist.apache.org/repos/dist/dev/iceberg/.
  • Print a draft [VOTE] email you can use on dev@iceberg.apache.org.

Send the [VOTE] email. The vote runs for at least 72 hours and requires three +1 votes from PMC members with no -1 votes to pass.

Publish

When the vote passes, run:

GH_TOKEN=${YOUR_GITHUB_TOKEN} dev/release/release.sh ${VERSION} ${RC}

release.sh moves the artifacts from https://dist.apache.org/repos/dist/dev/iceberg/ to https://dist.apache.org/repos/dist/release/iceberg/ (which feeds https://downloads.apache.org/iceberg/) and creates a GitHub Release with auto-generated notes.

Post-release tasks

After publishing, complete these steps:

  1. Add the release to ASF's report database at the Apache Committee Report Helper.
  2. Verify the GitHub Release at https://github.com/apache/iceberg-go/releases is correctly tagged, has generated release notes against the prior tag, and is marked as latest. release.sh runs gh release create ... --generate-notes --verify-tag so the release should already exist; double-check the notes and the "Latest" badge.
  3. Update Getting Started to pin the new release. Check the Go minimum and dependency versions against the tag's go.mod, then run the walkthrough in a fresh module. Update the release-tag link and version-specific flag notes in the CLI guide.
  4. Send the [ANNOUNCE] email to dev@iceberg.apache.org and announce@apache.org.
  5. File a release blog post in apache/iceberg under site/docs/blog/posts/. See the prior 0.5.0 post (2026-03-05-iceberg-go-0.5.0-release.md) for the frontmatter and structure.

Patch releases

dev/release/README.md does not document a patch-branch convention (e.g. iceberg-go-0.X.x). Confirm with the PMC on dev@iceberg.apache.org before cutting a patch release.

Other Iceberg implementations

Apache Iceberg Go is one of several official Iceberg implementations. Pick the one that matches your runtime; the table format and catalog protocols are the same across all of them.

When to use which

  • Java is the reference implementation and is what every query engine integrates against (Spark, Flink, Trino, Hive, Presto, Dremio, etc.). If you are running a JVM workload, this is the canonical choice.
  • PyIceberg is for Python and the dataframe ecosystem (PyArrow, Pandas, Polars, DuckDB, Daft, Ray). Most data-science and ML workflows live here.
  • iceberg-rust is the Rust implementation, used by pyiceberg-core, DataFusion-based engines, and other Rust-native systems.
  • iceberg-cpp is early-stage (0.2.0 released 2026-01-26). Track the project for native C++ integration once it stabilizes.
  • iceberg-go (this project) is for Go services and tooling. Tight Apache Arrow Go integration makes it a good fit for streaming Arrow record batches into and out of Iceberg tables.

Specifications and shared concepts

The Iceberg spec, terminology, partitioning semantics, evolution semantics, REST Catalog OpenAPI, and multi-engine support policy live with the main project at iceberg.apache.org. All the implementations above target the same spec.
